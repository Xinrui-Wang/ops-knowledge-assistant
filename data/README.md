# 样例数据说明

本目录的文档与数据**均为虚构**，仅用于演示与评测。公司与产品名称、金额、指标均为构造值。

## 一、制度文档（`docs/`）

| 文件 | 条款数 | 覆盖主题 |
| --- | --- | --- |
| `01-销售费用报销管理制度.md` | 11 条 | 住宿/交通/餐补/招待标准、审批权限、报销时限 |
| `02-差旅与出差管理办法.md` | 11 条 | 出差审批、交通工具标准、出差报告 |
| `03-售后服务响应管理办法.md` | 9 条 | 工单分级、首次响应与解决时限、满意度回访 |
| `04-渠道返利政策.md` | 8 条 | 返利阶梯、核算口径、发放方式 |
| `05-客户信息与数据安全规范.md` | 8 条 | 数据分级、导出审批、传输要求 |

文档结构：`# 一级标题` 为文档名，`## 第X章` 为章节，`**第X条（主题）**` 为条款正文。
RAG 的引用粒度到「文档标题 + 条款编号」。

## 二、运营数据库（`ops.db`）

由 `seed.py` 生成（固定种子，可重复）。生成物不入库。

| 表 | 行数 | 说明 |
| --- | --- | --- |
| `dim_region` | 5 | 大区维度 |
| `dim_product` | 5 | 产品维度 |
| `fact_sales` | 260 | 2026Q3 销售订单 |
| `fact_ticket` | 109 | 售后工单（响应/解决时长、满意度） |
| `fact_expense` | 220 | 费用报销单（住宿含晚数，可算每晚均价） |

机器可读的数据字典：`schema.json`（表注释 + 列注释，供 Text2SQL 的 schema linking 使用）。

指标口径：`metrics.json`（客单价、达标率等业务术语的计算方式）。查数前先对齐口径，
未登记的口径不做假设。

## 三、刻意埋的坑

### 1. 政策 ↔ 数据冲突

- 制度《销售费用报销管理制度》**第五条**：一线城市住宿每晚上限 **600 元**。
  数据：销售一部一线城市住宿实际均价 **> 600 元/晚**。
- 制度《售后服务响应管理办法》**第四条**：P2 工单首次响应 **2 小时**。
  数据：华东区 P2 工单平均首次响应 **> 120 分钟**。

设计意图：HYBRID 类问题必须**同时**给出制度条款与实际数据，并显式指出二者不一致，
而不是二选一——这正是作业里「冲突处理」的考察点。

### 2. 小样本异常

西北区第三季度仅有 **3 张订单**，且均为大额服务器订单，客单价显著高于其他大区。
任何「哪个大区客单价最高」的直接回答都会得到西北区，
但基于 3 个样本的结论不可靠——系统应主动标注样本量不足。

| --- | --- | --- | --- |
| 1 | 一线城市出差住宿标准是多少？ | RAG | 条款级引用（文档 + 第五条） |

| 3 | 华东区第三季度售后响应是否达标？ | HYBRID | 制度 2 小时 vs 实际数据 → 冲突呈现 |

| 5 | 哪个大区客单价最高？ | SQL | 小样本（西北区 n=3）不可比 |
